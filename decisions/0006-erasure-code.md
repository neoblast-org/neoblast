# 0006: Erasure code: Leopard-RS high-rate, checked against Leopard

- Status: accepted
- Date: 2026-10-14
- Settles: ROADMAP open item 7

## Context and problem statement

Parity shards are stored on disk and covered by the file root, so the erasure
code's exact output bytes are part of the format. They came from
`reed-solomon-simd` 3.1.0, a crate with a small blast radius (8 reverse
dependencies). If only that crate defined the bytes, every other implementation
(the planned SDKs, a future rewrite) would have to reproduce one crate's
internals, and a silent change in it would break every stored file.

`reed-solomon-simd` descends from Leopard-RS (catid/leopard, BSD-3-Clause), a C
library that implements the same Reed-Solomon codes over GF(2^16). The question:
does our output match Leopard byte for byte, and under which rules?

Decision rule, written before the check: **match → keep the crate and add a
differential test in CI; no match → the golden vectors become the spec and the
crate is vendored and frozen.**

## Method

A small C++ harness (`tools/leopard-vectors/harness.cpp`) printed Leopard's
recovery shards (commit `22ddc78`) for deterministic data, and a throwaway Rust
program printed `reed-solomon-simd`'s output for the same data with each of its
encoders. Recovery shards were compared by hash.

The exploratory sweep covered k/m of 1/1, 3/1, 4/3, 10/6, 16/16, 20/10, 20/20,
25/25, 32/32, 50/13, 64/64, 100/100, 200/56, 300/300 and 1000/24, each at shard
sizes 64, 128, 640, 4096 and 65536 (75 configurations). For m > k it covered
20/30 (our default 20-of-50), 10/40, 4/12, 16/48 and 20/108, plus k = 1 and the
format extremes 2/1, 2/126 and 64/1.

That sweep is not committed. What is reproducible from this repository is the
66-case subset in `tools/leopard-vectors/cases.txt`, which includes every
k/m shape above except k = 1, at fewer shard sizes.

## Findings

1. Leopard switches to an 8-bit field when n ≤ 256. With that disabled, Leopard
   and `reed-solomon-simd`'s **high-rate** encoder match on all 75 m ≤ k
   configurations of the sweep (1/1 included).
2. Leopard's API refuses `recovery_count > original_count`, but the algorithm
   does not need that limit. With that argument check removed (it appears in
   both `leo_encode` and `leo_decode`), Leopard
   matches the high-rate encoder for every m > k shape tested, including 20-of-50.
3. `reed-solomon-simd`'s default entry point (`encode`) picks low or high rate
   automatically. For 10/40, 4/12 and 16/48 it picks low rate, whose parity
   differs from Leopard. For 20/30 it happens to pick high rate.
4. k = 1 has no usable reference. Stock Leopard allows it only with m = 1 (n = 2),
   where the two match. For m > 1, Leopard's k = 1 shortcut reads input buffers
   that do not exist, and it crashes once the check is removed.
5. Leopard requires shard lengths that are multiples of 64 bytes. Our previous
   rule only required even lengths.
6. Stock Leopard (8-bit field on) produces different parity for small n. Leopard's
   newest commit (`910ad0a`) did not build in the test environment and was not used.
7. The SSSE3 and AVX2 builds of Leopard produce identical fixtures.

## Decision outcome

**Match.** We keep `reed-solomon-simd` =3.1.0 behind the `ErasureCode` trait. The
erasure code is defined as Leopard-RS's high-rate algorithm over GF(2^16), with
these format rules:

- always the high-rate encoder and decoder (`HighRateEncoder` /
  `HighRateDecoder`), never the automatic rate choice;
- `shard_len` rounds up to a multiple of 64 bytes (this supersedes the
  even-length rule from code-review issue 10);
- k ≥ 2, enforced in both `nbl-format` and `nbl-erasure`.

`spec/test-vectors/erasure-leopard.json` holds 66 cases of Leopard's own output,
regenerated by `tools/leopard-vectors/generate.sh`. Leopard is cloned at a pinned
commit and never vendored. `crates/nbl-erasure/tests/leopard_fixtures.rs` checks
every case on every CI run, in both directions: our parity equals Leopard's, and
our decoder rebuilds the data from Leopard's parity. It also fails if a case is
dropped from or added to the list in `cases.txt`.

### Consequences

- Good: the parity bytes are reproduced by two implementations in different
  languages (Leopard in C and its Rust descendant), so an SDK can be checked
  against either. A drifting dependency fails CI instead of
  silently changing stored files.
- Good: no vendoring and no new runtime dependencies. The test uses only crates
  already in the workspace.
- Bad: the 64-byte rounding wastes up to 63 bytes per shard: at most 0.03% for a
  full 4 MiB segment at 20-of-50, more for tiny files.
- Bad: this is a byte format change, so `phase1.json` was regenerated. Only the
  header's `shard_size` field moved (and the root, links and manifest hash that
  cover it). No version bump: nothing had been released or tagged, and Phase 1's
  "golden vectors frozen" gate had not been reached.
- Neutral: for m > k the reference is Leopard with its argument check removed,
  not stock Leopard. The fixture file names the build used for each case.

## Considered options

- **Vendor and freeze `reed-solomon-simd`.** This was the fallback if the check
  failed. It was not needed and would add about 7,600 lines of SIMD code to maintain.
- **Switch to an 8-bit-field code (for example `reed-solomon-erasure`).** That
  caps n at 256 and would leave the same problem of a single implementation
  defining the bytes.
- **Keep the even-length rule and accept Leopard incompatibility.** Rejected:
  Leopard is the only independent reference available.
