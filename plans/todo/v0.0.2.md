# Release v0.0.2

Status: in progress (started 2026-10-16). Owner: maintainer, with Claude doing
the code and docs.

**2026-10-16, maintainer's call:** v0.0.2 bundles every small open `crates/`
fix with four larger items:
- the CI identity check;
- heal robustness;
- heal memory;
- the segment-size decision.

One 24 h campaign then covers them all. S-002 (codeword consistency) and S-003
(read link via stdin) wait for a later release: S-002 needs a design decision
first.

## Success criteria

1. **CI checks every commit's identity (S-008).**
   - A hygiene step fails any commit after `5393f67`, merge commits included,
     whose author or committer is not `neoblast maintainers
     <dev@neoblast.dev>` in UTC.
   - It also fails any `Co-authored-by` or `Signed-off-by` trailer naming
     anyone else.
   - It prints only hashes, and fails if it cannot read the history.
   - It runs on every push and pull request. A bad commit is caught on its
     branch or pull request before the fast-forward to `main`.
2. **Fuzz tooling is pinned (S-004).** The nightly fuzz job installs
   `cargo-fuzz` 0.13.2 and uses `nightly-2026-10-14`, the compiler of the v0.0.1
   campaign. Step 7 re-pins both for the v0.0.2 campaign.
3. **Heal is robust against a hostile store (W-003, W-004, W-008).**
   - With a directory or planted `*.tmp` names at one missing shard's path,
     `heal` still rebuilds every other missing shard in every segment.
   - It then exits non-zero and names the path it could not write.
   - Regression tests cover both cases.
   - A test fails if `write_shard`'s symlinked-directory guard is removed.
4. **Writes are durable (W-007).**
   - Seal and heal sync each file before renaming it into place.
   - Afterwards they sync each parent directory: the store root and the
     segment directories.
   - Checked by reading the code and by a test that the sync calls are on every
     write path. A power cut cannot be tested.
5. **Seal and the library refuse early (W-005, W-006, W-009, W-010).**
   - A non-empty `--out` without `--force` is refused before any input is read,
     also from a pipe.
   - `--force` still keeps the old manifest when the new one would be too
     large.
   - `seal_stream` refuses parameters whose manifest would exceed
     `MAX_MANIFEST_LEN` before writing a shard. `write_manifest` checks the cap
     before encoding.
   - `--k 0` reports invalid k/n, and too many segments gives the
     `--segment-size` hint.
6. **Rejecting a planted manifest is cheap (S-005).**
   - Measured as `heal`'s peak RSS on the planted manifest from S-005 (just
     under the cap, k=2, n=3, 64-byte segments).
   - The peak is at most 1.2 times the manifest's size, instead of 3.2 times.
   - A regression test checks that the root is compared before any
     per-segment list is built.
7. **Heal's memory is flat.**
   - `bench/heal-heap.sh` on the reference Mac (peak live heap, counted exactly
     by dhat) shows heal's peak at 1 GiB above its peak at 256 MiB by no more
     than the manifest's own growth plus 64 KiB, for 1 MiB and 4 MiB segments.
   - The cause of the growth is named, and the `stream.rs` module doc matches.
   - Amended 2026-10-16, maintainer's call, after measuring: the first wording
     asked for peak RSS within 1 MiB. RSS varied by up to 8 MiB between
     identical runs, and at 1 MiB segments the manifest alone grows 1.21 MiB
     between the two files, so that could be neither judged nor met.
8. **Segment size decided (ROADMAP open item 2; `segment-size-decision.md`).**
   - Decision 0009 applies the rule fixed in ROADMAP item 2 to a committed
     `bench/segment-size.sh` record. The rule is working memory ≤ 32 MiB for
     seal, open, heal and open-from-parity.
   - The record comes from the reference Mac, measured on the code after
     criterion 7.
   - `Params::default()` changes only if the rule says so. The v1 vector files
     stay unchanged.
9. **Tests are tidy (W-011).** One `scratch` helper, in
   `crates/neoblast/tests/common/mod.rs`, serves every test file.
10. **Released like v0.0.1, without its problems.**
    - **Gate:**
      - `fuzz/campaign.sh summary` shows `met` ×5 on the final code;
      - both review logs cover the release commit with no open blocker.
    - **Merges:** every merge is a fast-forward with the project's identity
      (S-007). PRs are opened and merged only as `neoblast-dev`.
    - **Publish:** the crates go out through the Release workflow (trusted
      publishing, no token).
    - **Release:** a signed tag and a GitHub release by `neoblast-dev`.
    - **Process (S-006):** the review skill and `SECURITY.md` say that an
      unfixed finding of medium or higher severity stays out of the public repo
      until its fix merges.

### Step 5 results

2026-10-16 on the reference Mac, files sealed at 20-of-50 and healed after
losing 30 shards in every segment.

**What grew.** Apart from per-segment buffers, which are freed each time, only
the manifest grows with the file. Before #15 (S-005) heal held it about three
times over, partly as one small list per segment; after #15, twice (the bytes
the CLI read and the decoded manifest). #16 keeps one: `Manifest` holds its
encoding, `Manifest::decode_owned` takes the bytes over, and the CLI heals and
opens through `heal_manifest` and `open_manifest`. Between a 256 MiB and a
1 GiB file, three copies come to about 3.6 MiB at 1 MiB segments and 0.9 MiB
at 4 MiB segments. That is only part of the 5–8 MiB RSS growth measured in
Phase 1, where runs varied by up to 8.5 MiB; the rest is noise and memory the
system allocator keeps, which RSS counts and the live heap does not.

Peak live heap in MiB (`bench/heal-heap.sh`; exact, so one run each):

| File | Segment | `main` (`9478e6f`) | #16 | Manifest |
| --- | --- | --- | --- | --- |
| 256 MiB | 1 MiB | 14.51 | 14.11 | 0.40 |
| 1 GiB | 1 MiB | 16.93 | 15.32 | 1.61 |
| 256 MiB | 4 MiB | 29.51 | 29.41 | 0.10 |
| 1 GiB | 4 MiB | 30.11 | 29.71 | 0.40 |

On `main` heal grew by twice the manifest's growth; with #16 by exactly the
manifest's growth (0 bytes beyond it). The `main` column comes from the same
harness built against `9478e6f`, healing through `heal_stream` as its CLI did.
`bench/heal-heap/tests/` checks the copies exactly in every run of its tests:
`decode_owned` copies nothing, and `decode` copies only after the root
matches.

For reference, peak RSS on `main` in MiB (`bench/heal-check.sh`, median of
three; runs in brackets): 29.3 (29.3, 21.6, 29.3) and 30.7 (30.7, 26.5, 31.8)
at 1 MiB segments; 56.5 (55.0, 56.5, 61.2) and 55.8 (55.8, 54.1, 61.2) at
4 MiB. At 4 MiB segments RSS is about 26 MiB above the live heap: 11 MiB of
fixed cost (program and codec tables) and about 15 MiB that the system
allocator keeps after blocks are freed. That gap, not growth, is what decides
step 6; `exp/heal-reuse` (reusing the codec's buffers) is the lead for it.
